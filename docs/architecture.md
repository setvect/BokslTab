# BokslTab 아키텍처

현재 SwiftPM 구현의 책임과 실행 흐름을 설명한다. 초기 구현 계획은 `plan.md`를 참고한다.

## 모듈과 책임

| 모듈 | 책임 |
| --- | --- |
| `BokslTabCore` | 앱·창·탭 모델, 목록 조합, 선택 유지, MRU 순서, 어댑터 인터페이스 |
| `BokslTabMacOSAdapters` | CoreGraphics·Accessibility·AppKit 연동, 단축키 등록, 권한 조회, 진단 로그 |
| `BokslTabUI` | 단일 AppKit 패널, SwiftUI 목록, 키 입력과 반복, 화면 배치 |
| `BokslTabApp` | 서비스 조립과 `SwitcherCoordinator`의 표시·갱신·활성화 흐름 |

Core는 AppKit 및 Accessibility에 의존하지 않는다. App이 하나의 `MacOSAccessibilityService`를 만들어 창 목록 제공자와 창 활성화기에 주입한다.

## 창 목록 표시와 갱신

1. 시작 시와 새로운 전환 목록을 열 때 `requestRefresh(including:)`로 상세 조회를 예약한다.
2. 목록 읽기는 현재 CoreGraphics 창 정보와 이미 수집한 캐시로 즉시 결과를 만든다. 읽기 자체는 AX 조회를 예약하거나 기다리지 않는다.
3. AX 작업은 공유 서비스의 직렬 작업 큐에서 실행한다. 앱별 갱신 요청은 하나만 실행·대기할 수 있다.
4. 캐시 완료 알림은 50ms 동안 모아서 메인 큐에 전달한다. coordinator는 표시 중인 목록을 다시 읽고 선택 대상을 보존해 병합한다.
5. 패널과 hosting controller를 재사용한다. 항목 수에 따라 프레임을 다시 계산하므로 탭 확장 시 크기도 갱신된다.

`BackgroundRefreshCache`는 값의 유효 기간(5초), 갱신 간격(0.5초), 진행 중 요청과 오래된 결과 폐기를 관리한다. 앱의 응답 실패와 재시도 시점은 관리하지 않는다.

창 목록 관련 파일은 다음 책임으로 나눈다.

| 파일 | 책임 |
| --- | --- |
| `MacOSWindowCatalogProvider` | CG 목록과 AX·제목·이벤트 캐시를 조합하고 상세 갱신을 요청 |
| `AccessibilityWindowDiscovery` | 한 앱의 AX 창과 보조 창을 조회해 스냅샷 생성 |
| `WindowSnapshots` | 창 스냅샷, CG 정보 파싱, 합성 ID와 기하 정보 |
| `WindowCatalogPolicies` | 창 매칭, 제목 보완, 중복 제거 규칙 |
| `WindowTabCatalog` | 탭 지원 앱 판별, AX 탭 해석, 탭별 행 확장 |
| `AccessibilityWindowEventCache` | AX 이벤트 구독, 백그라운드 수집, 최근 창 보관 |
| `AccessibilityEventHistory` | 이벤트 이력의 보존·매칭·목록 변환 규칙 |
| `WindowTitleCache` | 제목 보완용 캐시와 개수 제한 |
| `SeenWindowRegistry` | 목록에 나온 창을 창 번호로 기억해 다른 Space·전체화면 창을 다시 목록에 넣고, AX 정보에 빠진 화면 창에 제목을 줌 |
| `WindowServerAccess` | 창 번호로 CG 표시 상태 확인, SkyLight로 다른 Space의 창 전환 |
| `AccessibilityWindowElementCache` | 창이 보일 때 얻은 AX 핸들을 창 번호로 기억해 다른 Space에 있어도 창을 올릴 수 있게 함 |

## 창 식별과 최근 사용 순서

CG 창과 AX 창은 창 번호로 짝짓는다. 같은 앱의 최대화 창은 위치·크기가 같고, CG 제목은 화면 기록 권한 없이는 비어 있어 번호 외에는 구별할 방법이 없다. AX 창의 번호는 HIServices의 비공개 함수 `_AXUIElementGetWindow`로 읽는다. AltTab·yabai도 쓰는 함수이며, 실행 시점에 찾고 없으면 위치·크기 매칭으로 물러난다.

- 목록: 번호가 같은 AX 창의 제목을 붙인다. 번호를 아는데 어느 CG 창과도 맞지 않는 AX 창은 최소화·다른 Space 같은 화면 밖 창이므로 그 제목을 다른 창에 주지 않는다. 위치·크기 매칭과 제목 보완은 번호를 읽지 못한 AX 창에만 적용한다.
- 숨긴 앱처럼 AX로만 보이는 창도 번호를 알면 실제 번호를 행 ID로 쓴다. 숨김 전후에 같은 행으로 이어진다.
- 활성화: 행의 창 번호와 같은 AX 창을 올린다. 맞는 창이 없으면 번호를 모르는 창 중에서만 제목으로 찾는다. 어느 쪽으로 찾았는지 `window-activation.target by=window-id|title` 로그에 남긴다.

### 다른 Space와 전체화면 창

전체화면 창은 자기만의 Space에 있다. CG의 화면 표시 목록은 지금 보이는 Space의 창만 주고, AX의 창 목록도 현재 Space의 창만 준다. 그래서 크롬처럼 두 Space에 창이 나뉜 앱은 다른 쪽 창이 목록에서 빠졌다.

- 기억: `SeenWindowRegistry`가 화면에서 목록에 나온 창을 창 번호·제목과 함께 기억한다. 화면 밖으로 나간 창은 CG가 아직 그 번호를 같은 앱 창으로 갖고 있고 최소화되지 않았으면 다시 목록에 넣는다. 닫힌 창은 이때 잊는다. 화면에 나온 적 없는 창(숨은 보조 창, BokslTab 실행 전부터 다른 Space에 있던 창)은 넣지 않는다. 탭으로 펼치는 앱은 기존 AX 이벤트 이력을 그대로 쓴다.
- AX 상세 정보는 5초가 지나면 쓰지 않는다. 이 기억은 그와 무관하게 남아 있어서, 전체화면 Space에서 연 첫 목록에도 다른 앱 창이 바로 나온다.
- 제목: 화면에 보이는 창도 AX 정보에서 빠질 수 있다. 전체화면 Space에서 받은 AX 정보에는 앱의 주 창 하나만 있고, 5초가 지난 정보는 쓰지 않는다. 제목 캐시는 앱마다 제목을 하나만 가진다. 그래서 같은 크기로 최대화한 두 창 중 하나만 제목을 얻고, 다른 하나는 제목 없는 중복 창으로 걸러졌다. 이제 AX 정보에 없는 창은 이 기억에 있는 자기 제목을 앱별 제목 캐시보다 먼저 쓴다. 앱별 캐시가 붙인 제목은 다른 창의 제목일 수 있어 기억하지 않는다.
- 손쉬운 사용 권한이 없어지면 제목 캐시와 함께 비운다.
- 전환: 대상이 화면 밖(다른 Space, 전체화면 Space, 최소화, 숨긴 앱)이면 SkyLight 비공개 함수로 그 창을 앞으로 가져오라고 요청한다(`_SLPSSetFrontProcessWithOptions`, `SLPSPostEventRecordTo`).
- 창 서버는 요청을 받아들여도 macOS가 현재 Space에 머무는 경우가 많았다(14번 중 11번). macOS는 앱이 직접 창을 올릴 때 그 Space로 따라간다. 그래서 창이 보일 때 얻은 AX 핸들을 창 번호로 기억해 둔다(`AccessibilityWindowElementCache`). 상세 조회와 전환 조회에서 AX가 창 목록을 줄 때마다 기록한다. SkyLight 요청 뒤에는 이 핸들로 최소화를 풀고 창을 올린다. AltTab·yabai와 같은 순서다. 핸들은 쓰기 전에 창 번호로 확인하고, 맞지 않으면 버린다.
- 결과는 `window-activation.target by=window-server axRaise=raised|failed|no-handle` 로그에 남는다. 0.6초 뒤 창이 실제로 보이는지는 `window-activation.window-server.verify visible=…` 로그에 남는다. SkyLight 함수가 없거나 실패하면 기존 AX 경로와 앱 활성화로 물러난다. 탭은 계속 AX로만 전환한다.

### 최근 사용 순서

MRU는 화면에 있는 창의 실제 쌓임 순서(CG front-to-back)를 기준으로 한다. 같은 앱 안에서 클릭으로 창을 바꾼 것처럼 앱 활성화 이력이 놓치는 변화도 쌓임 순서에는 반영된다.

활성화·선택 이력은 다른 Space·전체화면 창, 숨긴 앱의 창, 비활성 탭처럼 화면에 없는 항목의 자리를 정하는 데만 쓴다. 이런 항목은 다음 두 종류의 화면 항목보다 나중에 쓴 것이다. 그래서 그중 가장 위에 있는 항목 바로 앞에 놓는다.
- 이력에서 그 항목보다 뒤에 있는 화면 항목
- 이력에 한 번도 기록되지 않은 화면 항목

모든 화면 항목이 더 최근이면 목록 끝에 놓는다.

목록을 열 때는 화면 맨 위 창과 함께, 목록에 나오는 창 중 맨 위 창도 이력에 기록한다. 크롬 전체화면 Space의 맨 위 창은 목록에 없는 도구막대 창이다. 그 창만 기록하면 BokslTab을 거치지 않고 들어간 전체화면 창은 이력에 남지 않는다. 그러면 그 Space를 떠난 뒤 목록 끝으로 밀린다.

## 응답 제한과 활성화

`MacOSAccessibilityService`가 앱별 재시도 제한을 단독으로 소유한다. 조회·이벤트 감시·활성화 모두 같은 상태를 사용한다. 응답 실패 또는 요청 시간 소진 시 해당 앱에 15초 동안 추가 AX 요청을 보내지 않는다. 대기 중 재요청으로 제한 시간이 연장되지 않는다.

`AccessibilityQueryBudget`는 각 작업에 명시적으로 전달한다. 전역 변수나 스레드 사전에 의존하지 않는다. 모든 AX 속성 읽기·쓰기·동작 요청과 이벤트 구독에 제한을 적용한다.

- 창 정보 조회: 개별 호출 최대 80ms, 한 앱의 작업 최대 250ms.
- 창 올리기·탭 선택: 개별 호출 최대 250ms, 작업 최대 1초.
- 실제 제한은 남은 시간과 개별 호출 제한 중 작은 값이다. 이미 시작한 시스템 호출의 반환은 OS 타임아웃에 따른다.

창 활성화는 비동기 인터페이스다. AX 대상 식별과 동작은 작업 큐에서 실행하고, 앱을 앞으로 가져오는 AppKit 호출과 결과 반영은 메인 액터에서 실행한다. 새 전환 요청이나 종료는 이전 작업을 취소한다. 취소된 작업은 대기 이후 앱 포커스를 변경하거나 다음 AX 동작을 시작하지 않는다. 이미 전달된 시스템 동작을 되돌리지는 않는다.

창을 정확히 찾지 못하거나 AX 요청이 지연되면 앱 활성화로 대체한다. 현재 선택한 탭을 찾지 못한 경우 다른 탭으로 임의 전환하지 않는다.

## 단축키 등록

`GlobalHotkeyServicing.start`가 실패하면 등록을 모두 정리한다. Carbon과 우선순위 서비스 모두 이 계약을 따른다. 활성 앱 단축키 등록 실패 시 coordinator가 기본 Cmd+Tab만 다시 등록하고, 성공 후 제한 상태를 알린다.

macOS 기본 Cmd+Tab 설정의 변경·복원은 `NativeCommandTabHotkeyService`가 담당한다. 우선순위 서비스는 native override, EventTap, Carbon 사용 순서를 결정한다.

## 로그와 테스트

앱 시작 시 파일 로그를 활성화한다. 라이브러리와 테스트에서는 기본적으로 사용자의 로그 파일에 기록하지 않는다. 파일 쓰기와 날짜 포맷은 별도 직렬 큐에서 처리한다. 현재 로그와 이전 로그를 각각 최대 5MiB로 제한한다. `--debug-logging`을 지정하면 창 목록의 상세 진단도 기록한다.

테스트는 Core 상태, 창·탭 정책, 캐시, AX 시스템 경계, 단축키 수명 주기, 패널 배치, coordinator 통합으로 구분한다. AX API를 교체해 실제 제한·재시도·취소 코드가 실행되도록 검증한다. 실제 앱의 권한 및 창·탭 전환은 별도 수동 검증 대상이다.

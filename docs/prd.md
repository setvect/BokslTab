# BokslTab PRD

## 1. 문제 정의

macOS 기본 앱 전환은 빠르지만, 사용자가 실행 중인 앱을 명확한 리스트로 보고 원하는 앱을 키보드로 고르는 흐름은 제한적이다. 특히 여러 앱이 실행 중일 때 현재 전환 가능한 앱을 아이콘과 이름 중심으로 빠르게 확인하고 이동하는 작은 도구가 필요하다.

BokslTab은 이 문제를 해결하는 완성형 제품이 아니라, AltTab 스타일 앱 전환기의 최소 흐름을 구현해보며 OMX/Codex 기반 요구사항 정리, 계획, 구현, 검증 프로세스를 실험하기 위한 프로토타입이다.

## 2. 제품 목표

1. macOS에서 실행 중인 앱을 빠르게 확인한다.
2. 사용자가 키보드만으로 앱을 선택하고 전환한다.
3. 모든 실행 앱 모드와 활성 앱/윈도우 앱 모드를 구분해 검증한다.
4. 창 썸네일 없이 아이콘과 타이틀만으로 충분한 전환 경험을 제공할 수 있는지 확인한다.
5. OMX/Codex를 활용한 문서화→계획→구현→검증 워크플로우를 실험한다.

## 3. 대상 사용자

- macOS에서 여러 앱을 오가며 작업하는 개발자 또는 파워 유저
- 키보드 중심으로 앱을 전환하고 싶은 사용자
- BokslTab 프로젝트의 MVP 구현/검증 과정을 실험하려는 개발자
- 완성형 앱보다 빠른 프로토타입과 학습을 우선하는 프로젝트 소유자

## 4. 사용자 Pain Point

| Pain Point | 설명 |
| --- | --- |
| 실행 앱 파악 어려움 | 여러 앱이 떠 있을 때 어떤 앱으로 이동할지 빠르게 확인하기 어렵다 |
| 기본 전환 UI의 제한 | 기본 앱 전환은 사용자가 원하는 필터링/표시 방식을 실험하기 어렵다 |
| 창 썸네일의 복잡도 | 창 캡처/썸네일은 권한과 구현 복잡도가 커서 초기 실험에 부담이 된다 |
| 프로세스 검증 필요 | 요구사항부터 검증까지 OMX/Codex가 얼마나 잘 지원하는지 확인하고 싶다 |

## 5. 제품 가설

1. 창 썸네일 없이 앱 아이콘과 타이틀만 제공해도 MVP 수준의 빠른 앱 전환 경험을 검증할 수 있다.
2. 모든 실행 앱 모드와 활성 앱/윈도우 앱 모드를 분리하면 사용자에게 의미 있는 전환 범위 차이를 제공할 수 있다.
3. 키보드 중심 조작만으로도 1차 프로토타입의 핵심 사용성은 충분히 검증할 수 있다.
4. Swift/SwiftUI/AppKit 기반의 작은 macOS 앱은 이 MVP를 빠르게 구현하고 검증하기에 적합하다.

## 6. MVP 정의

BokslTab MVP는 다음 조건을 만족하는 macOS 앱 프로토타입이다.

- 전역 단축키로 앱 전환 UI를 열 수 있다.
- 최소 2가지 모드를 제공한다.
  - 모든 실행 앱 모드
  - 활성 앱 또는 현재 윈도우가 있는 앱 모드
- 앱 리스트에는 앱 아이콘과 앱 타이틀이 표시된다.
- 사용자는 키보드로 선택 항목을 이동할 수 있다.
- 사용자는 선택한 앱으로 전환할 수 있다.
- 사용자는 전환을 취소할 수 있다.
- 화면 캡처, 창 썸네일, 창 단위 전환, 설정 UI는 포함하지 않는다.

## 7. 핵심 사용자 흐름

### Flow 1. 모든 앱 전환

1. 사용자가 여러 앱을 실행한다.
2. 사용자가 모든 앱 모드 단축키를 누른다.
3. BokslTab이 모든 실행 앱 리스트를 표시한다.
4. 사용자가 키보드로 앱을 선택한다.
5. 사용자가 선택을 확정한다.
6. 선택한 앱이 활성화된다.

### Flow 2. 활성 앱/윈도우 앱 전환

1. 사용자가 현재 작업 중인 앱들 사이를 빠르게 오가고 싶다.
2. 사용자가 활성 앱/윈도우 앱 모드 단축키를 누른다.
3. BokslTab이 현재 전환 가치가 높은 앱 리스트를 표시한다.
4. 사용자가 키보드로 앱을 선택한다.
5. 선택한 앱이 활성화된다.

### Flow 3. 취소

1. 사용자가 단축키로 앱 리스트를 연다.
2. 사용자가 전환하지 않기로 한다.
3. 사용자가 `Escape`를 누른다.
4. UI가 닫히고 기존 앱 포커스가 유지된다.

## 8. 기능 우선순위

### P0 — MVP 필수

- macOS 앱 셸
- 실행 앱 목록 조회
- 앱 아이콘/타이틀 표시
- 전환 UI 표시/닫기
- 키보드 선택 이동
- 선택 앱 활성화
- 모든 앱 모드 단축키
- 활성 앱/윈도우 앱 모드 단축키
- 취소 동작
- 기본 예외 처리

### P1 — MVP 안정화

- 권한 부족 안내
- 앱 목록 정렬 개선
- 아이콘 캐싱
- 윈도우 보유 앱 필터 정확도 개선
- 단축키 충돌 시 대체값 적용
- 핵심 로직 단위 테스트

### P2 — MVP 이후

- 사용자 설정 UI
- 창 단위 전환
- 창 썸네일/미리보기
- 디자인 개선 및 애니메이션
- 다국어 지원
- 배포/서명/공증 자동화
- 업데이트 기능

## 9. 성공 기준

### 제품 성공 기준

- 사용자가 전역 단축키로 앱 리스트를 열 수 있다.
- 리스트에서 앱 아이콘과 앱 타이틀을 확인할 수 있다.
- 사용자가 키보드로 선택 항목을 이동할 수 있다.
- 선택한 앱으로 실제 전환된다.
- 모든 앱 모드와 활성 앱/윈도우 앱 모드를 구분해 시연할 수 있다.
- 창 썸네일 없이도 기본 전환 흐름이 이해 가능하다.

### 프로세스 성공 기준

- `docs/requirements.md`와 `docs/prd.md`가 작성되어 구현 계획의 기준 문서가 된다.
- 요구사항, PRD, 구현 계획, 검증 결과가 추적 가능한 형태로 남는다.
- MVP 범위와 제외 범위가 명확해 구현 중 범위 확장을 줄인다.

## 10. 리스크

| 리스크 | 영향 | 대응 |
| --- | --- | --- |
| 전역 단축키 충돌 | 사용자가 단축키로 UI를 열지 못함 | 충돌 적은 기본값 선택, 코드 상수로 빠르게 변경 가능하게 설계 |
| 접근성 권한 필요 | 전환 또는 키 입력 처리가 제한될 수 있음 | 권한 안내 제공, 권한 없는 상태의 fallback 정의 |
| 윈도우 앱 판별 부정확 | 활성 앱/윈도우 앱 모드 품질 저하 | CoreGraphics 기반 판별 후 실패 시 실행 앱 fallback |
| 앱 활성화 실패 | 일부 앱으로 전환되지 않음 | 실패를 안전하게 처리하고 로그 기록 |
| MVP 범위 확장 | 실험 속도 저하 | 썸네일, 창 단위 전환, 설정 UI를 명시적으로 제외 |
| macOS 버전 차이 | API 동작 차이 발생 | 타깃 macOS 버전 결정 후 구현 단계에서 확인 |
| 의존성 선택 문제 | 단축키 구현 지연 | 네이티브 API 우선, 필요 시 작은 검증된 Swift Package 검토 |

## 12. 구현 전 확인해야 할 질문

- 타깃 macOS 최소 버전은 무엇인가?
- SwiftUI 중심으로 갈지, AppKit 중심으로 갈지 최종 결정이 필요한가?
- 전역 단축키 구현에 외부 Swift Package를 허용할 것인가?
- 기본 단축키를 무엇으로 확정할 것인가?
- 앱 목록 정렬 기준은 무엇인가?
- 활성 앱/윈도우 앱 모드에서 “윈도우가 있는 앱”의 정확한 정의는 무엇인가?
- 접근성 권한이 필요한 경우 어떤 수준의 안내 UI를 제공할 것인가?
- MVP 검증은 수동 시연만으로 충분한가, 아니면 XCTest 기반 단위 테스트까지 포함할 것인가?
- 앱 자체를 메뉴바 앱으로 만들 것인가, 일반 macOS 앱으로 만들 것인가?

## 13. MVP 비목표 요약

- 완성형 제품 출시가 아니다.
- 창 썸네일을 만들지 않는다.
- 창 단위 전환을 만들지 않는다.
- 설정 UI를 만들지 않는다.
- 배포/서명/공증 자동화를 하지 않는다.
- 디자인 완성도를 MVP 성공 기준으로 삼지 않는다.

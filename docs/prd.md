# BokslTab PRD

## 1. 문제 정의

macOS 기본 `Cmd+Tab`은 앱 중심 전환을 제공한다. 이 방식은 앱이 하나의 작업 단위였던 환경에서는 일관성이 있지만, Chrome, VS Code, Finder처럼 하나의 앱 안에 여러 독립 창/작업 공간을 열어두는 현대 작업 방식에서는 불편하다.

Windows의 `Alt+Tab`에 익숙한 사용자는 “앱”이 아니라 “창”을 실제 작업 단위로 인식한다. Chrome 창을 여러 개 열었는데 macOS `Cmd+Tab`에는 Chrome이 하나만 보이면, 사용자는 원하는 작업 창으로 바로 이동할 수 없다.

BokslTab은 이 문제를 겨냥한 macOS용 AltTab 스타일 앱/창 전환기 프로토타입이다. 완성형 제품이 아니라, 창 단위 전환을 포함한 최소 흐름을 구현해보며 OMX/Codex 기반 요구사항 정리, 계획, 구현, 검증 프로세스를 실험하기 위한 MVP이다.

## 2. 제품 목표

1. macOS에서 실행 중인 앱과 창을 빠르게 확인한다.
2. 사용자가 키보드만으로 앱/창을 선택하고 전환한다.
3. 모든 앱/창 모드와 활성 앱 창 모드를 구분해 검증한다.
4. 창 썸네일 없이 아이콘과 창/앱 타이틀만으로 충분한 전환 경험을 제공할 수 있는지 확인한다.
5. macOS 기본 `Cmd+Tab`의 앱 중심 한계를 보완하는 창 중심 전환 UX를 실험한다.
6. OMX/Codex를 활용한 문서화→계획→구현→검증 워크플로우를 실험한다.

## 3. 대상 사용자

- Windows `Alt+Tab`처럼 창 단위 전환을 기대하는 macOS 사용자
- Chrome, VS Code, Finder 등 한 앱에서 여러 창을 자주 쓰는 사용자
- macOS 기본 `Cmd+Tab`이 아이콘 중심/앱 중심이라 불편하다고 느끼는 사용자
- 키보드 중심으로 앱과 창을 전환하고 싶은 개발자 또는 파워 유저
- BokslTab 프로젝트의 MVP 구현/검증 과정을 실험하려는 개발자

## 4. 사용자 Pain Point

| Pain Point | 설명 |
| --- | --- |
| `Cmd+Tab`의 앱 중심 한계 | 같은 앱의 여러 창이 하나의 앱 아이콘으로 묶여 원하는 창에 바로 갈 수 없다 |
| 아이콘만으로 부족한 식별성 | macOS 기본 전환 UI는 창 제목/작업 맥락을 충분히 보여주지 않는다 |
| Chrome/VS Code 멀티창 불편 | 업무용/개인용/프로젝트별 창이 모두 독립 작업인데 기본 전환에서는 구분이 약하다 |
| Mission Control의 과함 | 전체 창을 시각적으로 펼치는 방식은 빠른 키보드 전환에는 부담이 될 수 있다 |
| 창 썸네일의 구현 복잡도 | 썸네일은 유용하지만 권한과 구현 복잡도가 커서 MVP에는 부담이다 |
| 프로세스 검증 필요 | 요구사항부터 검증까지 OMX/Codex가 얼마나 잘 지원하는지 확인하고 싶다 |

## 5. 제품 가설

1. macOS 사용자도 Windows `Alt+Tab`처럼 창 단위 전환을 제공받으면 전환 비용이 줄어든다.
2. 창 썸네일 없이 앱 아이콘과 창 제목만 제공해도 MVP 수준의 빠른 창 전환 경험을 검증할 수 있다.
3. 모든 앱/창 모드와 활성 앱 창 모드를 분리하면 “전체 작업 전환”과 “현재 앱 내부 창 전환”을 모두 빠르게 처리할 수 있다.
4. 키보드 중심 조작만으로도 1차 프로토타입의 핵심 사용성은 충분히 검증할 수 있다.
5. Swift/SwiftUI/AppKit 및 macOS Accessibility/CoreGraphics API 기반의 작은 앱은 이 MVP를 빠르게 구현하고 검증하기에 적합하다.

## 6. MVP 정의

BokslTab MVP는 다음 조건을 만족하는 macOS 앱/창 전환기 프로토타입이다.

- 전역 단축키로 전환 UI를 열 수 있다.
- 최소 2가지 모드를 제공한다.
  - 모든 앱/창 모드: 여러 앱과 각 앱의 창을 한 리스트에 표시하고 전환한다.
  - 활성 앱 창 모드: 현재 활성 앱의 여러 창을 리스트에 표시하고 전환한다.
- 리스트 항목에는 앱 아이콘과 창/앱 타이틀이 표시된다.
- 같은 앱의 여러 창은 가능한 경우 각각 별도 항목으로 표시된다.
- 사용자는 키보드로 선택 항목을 이동할 수 있다.
- 사용자는 선택한 창 또는 앱으로 전환할 수 있다.
- 사용자는 전환을 취소할 수 있다.
- 화면 캡처, 창 썸네일, 설정 UI는 포함하지 않는다.

## 7. 핵심 사용자 흐름

### Flow 1. 모든 앱/창 전환

1. 사용자가 여러 앱과 여러 창을 실행한다.
2. 사용자가 모든 앱/창 모드 단축키를 누른다.
3. BokslTab이 모든 전환 가능한 앱/창 리스트를 표시한다.
4. 리스트는 앱 아이콘과 창/앱 타이틀을 함께 보여준다.
5. 사용자가 키보드로 원하는 항목을 선택한다.
6. 사용자가 선택을 확정한다.
7. 선택한 창 또는 앱이 활성화된다.

### Flow 2. 활성 앱 창 전환

1. 사용자가 VS Code 또는 Chrome처럼 여러 창을 가진 앱에서 작업 중이다.
2. 사용자가 활성 앱 창 모드 단축키를 누른다.
3. BokslTab이 현재 활성 앱에 속한 창 리스트를 표시한다.
4. 사용자가 키보드로 원하는 창을 선택한다.
5. 선택한 창이 활성화된다.

### Flow 3. 취소

1. 사용자가 단축키로 앱/창 리스트를 연다.
2. 사용자가 전환하지 않기로 한다.
3. 사용자가 `Escape`를 누른다.
4. UI가 닫히고 기존 앱/창 포커스가 유지된다.

## 8. 참고 이미지 기반 UI 방향

- `temp/모든앱 리스트업 표시 및 전환.png`
  - 여러 앱과 여러 창이 하나의 목록에 표시된다.
  - 항목은 앱 아이콘 + 창/앱 타이틀로 구성된다.
  - 같은 앱의 여러 창이 별도 항목으로 존재할 수 있다.
- `temp/활성화된 앱 리스트업 표시 및 전환.png`
  - 현재 활성 앱의 여러 창만 표시된다.
  - 예시에서는 VS Code의 프로젝트/문서 창들이 별도 항목으로 표시된다.
- 공통 UI 방향
  - 어두운 반투명 패널
  - 큰 텍스트
  - 파란색 선택 하이라이트
  - 썸네일 없는 단순 리스트

## 10. 성공 기준

### 제품 성공 기준

- 사용자가 전역 단축키로 모든 앱/창 리스트를 열 수 있다.
- 사용자가 전역 단축키로 현재 활성 앱의 창 리스트를 열 수 있다.
- 리스트에서 앱 아이콘과 창/앱 타이틀을 확인할 수 있다.
- 같은 앱의 여러 창이 각각 독립 항목으로 표시된다.
- 사용자가 키보드로 선택 항목을 이동할 수 있다.
- 선택한 창 또는 앱으로 실제 전환된다.
- 창 썸네일 없이도 기본 전환 흐름이 이해 가능하다.

### 프로세스 성공 기준

- `docs/requirements.md`와 `docs/prd.md`가 창 단위 전환을 MVP 필수 범위로 반영한다.
- 요구사항, PRD, 구현 계획, 검증 결과가 추적 가능한 형태로 남는다.
- MVP 범위와 제외 범위가 명확해 구현 중 범위 확장을 줄인다.

## 11. 리스크

| 리스크 | 영향 | 대응 |
| --- | --- | --- |
| 창 단위 전환 API 제약 | 선택한 창을 정확히 앞으로 가져오지 못할 수 있음 | Accessibility API/CoreGraphics/AppKit 조합을 사전 검증 |
| 접근성 권한 필요 | 창 전환 또는 키 입력 처리가 제한될 수 있음 | 권한 안내 제공, 권한 없는 상태의 fallback 정의 |
| 창 제목 조회 권한 문제 | 창 타이틀 표시가 제한될 수 있음 | 권한 요구 API 확인, fallback 타이틀 제공 |
| 전역 단축키 충돌 | 사용자가 단축키로 UI를 열지 못함 | 충돌 적은 기본값 선택, 코드 상수로 빠르게 변경 가능하게 설계 |
| 창 목록 부정확 | 목록에 불필요한 창이 보이거나 일부 창 누락 | 필터링 규칙을 단순하게 시작하고 검증 중 개선 |
| 앱/창 활성화 실패 | 일부 항목으로 전환되지 않음 | 실패를 안전하게 처리하고 앱 단위 fallback 또는 로그 기록 |
| MVP 범위 확장 | 실험 속도 저하 | 썸네일, 설정 UI, 배포 품질을 명시적으로 제외 |
| macOS 버전 차이 | API 동작 차이 발생 | 타깃 macOS 버전 결정 후 구현 단계에서 확인 |
| 의존성 선택 문제 | 단축키/창 전환 구현 지연 | 네이티브 API 우선, 필요 시 작은 검증된 Swift Package 검토 |

## 14. MVP 비목표 요약

- 완성형 제품 출시가 아니다.
- 창 썸네일을 만들지 않는다.
- 설정 UI를 만들지 않는다.
- 배포/서명/공증 자동화를 하지 않는다.
- 디자인 완성도를 MVP 성공 기준으로 삼지 않는다.
- 창 이동/리사이즈/정렬 같은 윈도우 매니저 기능은 만들지 않는다.

## 15. 이전 정의에서 변경된 점

초기 문서에서는 앱 단위 전환을 MVP 중심으로 두고 창 단위 전환을 제외했다. 그러나 사용자 피드백과 참고 이미지 확인 결과, BokslTab의 핵심 문제는 macOS `Cmd+Tab`이 같은 앱의 여러 창을 구분하지 못한다는 점이다. 따라서 **창 단위 전환은 MVP 필수 요구사항**으로 변경한다.

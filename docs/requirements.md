# BokslTab 요구사항 정의서

## 1. 프로젝트 요약

BokslTab은 macOS용 AltTab 스타일 **앱/창 전환기** 프로토타입이다. 사용자가 macOS에서 실행 중인 앱과 각 앱의 창을 빠르게 확인하고, 키보드로 선택해 해당 앱 또는 창으로 전환할 수 있게 한다.

1차 MVP는 완성형 제품이 아니라 OMX/Codex를 활용한 요구사항 정리, 계획, 구현, 검증 과정을 실험하기 위한 작은 프로토타입이다. 따라서 제품화 수준의 설정, 배포, 디자인 완성도보다 “Windows Alt+Tab처럼 실제 작업 단위인 창을 보고 전환할 수 있는가”를 검증하는 데 집중한다.

## 2. 용어 정의

| 용어 | 정의 |
| --- | --- |
| BokslTab | macOS용 앱/창 전환기 프로토타입 앱 |
| 앱 전환기 | 실행 중인 앱 또는 앱 창 목록을 보여주고 선택한 대상으로 포커스를 이동하는 UI/기능 |
| 창 전환 | 같은 앱 또는 여러 앱에 속한 개별 창을 선택해 해당 창/앱으로 이동하는 동작 |
| 모든 앱/창 모드 | 실행 중인 여러 앱과 각 앱의 전환 가능한 창을 한 리스트에 표시하는 모드 |
| 활성 앱 창 모드 | 현재 활성화된 앱의 여러 창을 리스트로 표시하고 전환하는 모드 |
| 리스트 항목 | 전환 가능한 앱 또는 창 단위 항목 |
| 앱 아이콘 | 리스트 항목이 속한 macOS 앱의 대표 아이콘 |
| 항목 타이틀 | 창 제목 또는 앱 이름. 창이 있으면 창 제목을 우선 표시한다 |
| 선택 항목 | 리스트에서 현재 키보드 포커스를 가진 항목 |
| 전환 | 선택한 앱 또는 창을 foreground로 활성화하는 동작 |
| 전역 단축키 | BokslTab이 포커스되어 있지 않아도 전환기를 여는 키 입력 |

## 3. 참고 이미지에서 확인한 UI 의도

`temp` 디렉토리의 PNG 2개를 기준으로 MVP UI 의도를 다음처럼 해석한다.

### 3.1 모든 앱 리스트업 표시 및 전환

- 파일: `temp/모든앱 리스트업 표시 및 전환.png`
- 의도: 여러 앱의 전환 가능한 항목을 한 리스트에 표시한다.
- 각 항목은 앱 아이콘과 창/앱 타이틀을 함께 보여준다.
- Chrome, VS Code, 터미널, AltTab, Brave, Slack 등 서로 다른 앱 항목이 한 목록에 섞여 있다.
- VS Code처럼 같은 앱의 여러 창/프로젝트가 각각 별도 항목으로 표시될 수 있어야 한다.

### 3.2 활성화된 앱 리스트업 표시 및 전환

- 파일: `temp/활성화된 앱 리스트업 표시 및 전환.png`
- 의도: 현재 활성화된 앱의 창들을 리스트업한다.
- 예시 이미지는 VS Code의 여러 창/프로젝트가 각각 별도 항목으로 표시된다.
- 즉, 이 모드는 “활성 앱 자체 목록”이 아니라 **활성 앱 내부의 창 목록 전환**으로 정의한다.

## 4. 기능 요구사항

### FR-1. 모든 앱/창 리스트 표시

- 사용자는 전역 단축키로 모든 앱/창 모드 전환 UI를 열 수 있어야 한다.
- 모든 앱/창 모드는 macOS에서 실행 중인 일반 앱과 전환 가능한 창을 목록으로 표시해야 한다.
- 창을 가진 앱은 가능한 경우 창 단위로 항목을 표시한다.
- 창 정보가 없거나 창 단위 전환이 불가능한 앱은 앱 단위 항목으로 표시할 수 있다.
- 시스템/백그라운드 프로세스처럼 사용자 전환 대상이 아닌 항목은 MVP에서 제외할 수 있다.
- 현재 실행 중인 BokslTab 자체는 전환 대상에서 제외하는 것을 기본값으로 한다.

### FR-2. 활성 앱 창 리스트 표시

- 사용자는 별도 전역 단축키로 활성 앱 창 모드 전환 UI를 열 수 있어야 한다.
- 활성 앱 창 모드는 현재 foreground 앱에 속한 전환 가능한 창을 목록으로 표시해야 한다.
- 예: VS Code가 활성 앱이고 여러 프로젝트 창이 열려 있으면 각 프로젝트 창을 별도 항목으로 표시한다.
- 활성 앱에 창이 하나뿐이면 해당 창 하나만 표시하거나 UI를 열지 않는 fallback을 허용한다.
- 활성 앱의 창 목록 조회가 macOS 권한/API 제약으로 실패하면 안전하게 실패하거나 앱 단위 전환으로 degrade할 수 있다.

### FR-3. 창 단위 전환

- 사용자는 리스트에서 선택한 창으로 전환할 수 있어야 한다.
- 같은 앱의 여러 창이 있을 경우 각 창은 독립 선택 항목이어야 한다.
- 선택한 창으로 정확히 포커스를 이동하는 것이 목표이다.
- macOS API 제약으로 창 직접 활성화가 어려운 경우, 앱 활성화 후 해당 창을 앞으로 가져오는 보조 방식 또는 접근성 API 사용을 검토한다.
- 정확한 창 전환이 불가능한 환경에서는 실패를 안전하게 처리하고, 문서/로그에 제약을 남겨야 한다.

### FR-4. 앱 아이콘 표시

- 앱 리스트 각 항목은 해당 항목이 속한 앱 아이콘을 표시해야 한다.
- 같은 앱의 여러 창은 동일 앱 아이콘을 사용한다.
- 아이콘을 가져올 수 없는 앱은 기본 placeholder 아이콘을 사용할 수 있다.

### FR-5. 항목 타이틀 표시

- 창 항목은 창 제목을 우선 표시해야 한다.
- 필요하면 `창 제목 — 앱 이름` 형식으로 표시한다.
- 앱 단위 fallback 항목은 앱 이름을 표시한다.
- 타이틀의 기본 우선순위는 창 제목 → localized app name → bundle name → process name으로 한다.

### FR-6. 키보드 선택 이동

- 앱/창 리스트가 열려 있는 동안 사용자는 키보드로 선택 항목을 이동할 수 있어야 한다.
- 기본 조작은 다음을 가정한다.
  - `Tab` 또는 `ArrowDown`: 다음 항목 선택
  - `Shift+Tab` 또는 `ArrowUp`: 이전 항목 선택
  - `Enter` 또는 단축키 release: 선택한 앱/창으로 전환
  - `Escape`: 전환 취소 및 UI 닫기

### FR-7. 선택한 앱/창으로 전환

- 사용자가 전환 확정 키를 입력하면 BokslTab은 선택된 앱 또는 창을 활성화해야 한다.
- 창 항목은 가능한 경우 해당 창을 전면으로 가져와야 한다.
- 선택한 앱/창이 이미 종료되었거나 활성화에 실패하면 UI를 닫고 실패 상태를 안전하게 처리해야 한다.

### FR-8. 모드별 단축키 매핑

- MVP는 최소 2개의 전환 모드에 각각 단축키를 매핑해야 한다.
  - 모든 앱/창 모드
  - 활성 앱 창 모드
- 단축키 기본값은 구현 단계에서 충돌 가능성을 고려해 정하되, 문서상 기본 가정은 다음과 같다.
  - 모든 앱/창 모드: `Option+Tab`
  - 활성 앱 창 모드: `Option+Backtick` 또는 충돌이 적은 대체 조합
- 단축키 사용자 설정 UI는 MVP 범위에서 제외한다.

## 5. 비기능 요구사항

### NFR-1. 단순성

- MVP는 핵심 앱/창 전환 흐름을 검증하는 최소 구현이어야 한다.
- 복잡한 설정, 애니메이션, 디자인 시스템, 배포 자동화는 후순위로 둔다.

### NFR-2. 응답성

- 단축키 입력 후 앱/창 리스트 UI는 체감상 즉시 표시되어야 한다.
- 창 목록 조회와 아이콘 로딩이 느린 경우에도 UI가 멈추지 않도록 캐싱 또는 지연 로딩을 고려한다.

### NFR-3. 안정성

- 권한 부족, 창 종료, 앱 종료, 빈 목록, 전환 실패 상황에서 앱이 크래시하지 않아야 한다.
- 예외 상황은 콘솔 로그 또는 개발용 로그로 확인할 수 있어야 한다.

### NFR-4. macOS 친화성

- macOS의 앱/창 활성화 규칙, 권한 정책, 샌드박스 제약을 고려해야 한다.
- MVP는 Mac App Store 배포 품질보다 로컬 개발/실험 가능성을 우선한다.

### NFR-5. 검증 가능성

- 요구사항은 수동 시연과 기본 자동 테스트가 가능한 형태로 작성되어야 한다.
- 핵심 로직은 UI와 분리해 단위 테스트가 가능하도록 설계하는 것을 권장한다.

## 6. MVP 범위

MVP에 포함한다.

1. macOS 앱으로 실행 가능한 최소 앱 셸
2. 전역 단축키 2개 등록
3. 모든 앱/창 목록 표시
4. 현재 활성 앱의 창 목록 표시
5. 앱 아이콘 및 창/앱 타이틀 표시
6. 키보드로 선택 이동
7. 선택 앱/창 활성화
8. 취소 동작
9. 권한 부족/빈 목록/전환 실패에 대한 안전 처리
10. `docs/requirements.md`, `docs/prd.md` 기반의 구현 계획 및 검증 실험

## 7. 제외 범위

MVP에서 제외한다.

- 창 썸네일, 화면 캡처, 실시간 미리보기
- Mission Control 수준의 윈도우 관리
- 창 이동/리사이즈/정렬 기능
- 드래그 앤 드롭 또는 마우스 중심 조작
- 단축키 사용자 설정 UI
- 환경설정 화면
- 다국어 지원
- 앱 자동 업데이트
- Mac App Store 배포
- 코드 서명/공증 자동화
- 완성형 디자인 시스템
- 복잡한 애니메이션
- 사용량 분석/텔레메트리

> 변경 사항: 초기 문서에서는 창 단위 전환을 제외했으나, 사용자 피드백과 참고 이미지 확인 후 **창 단위 전환은 MVP 필수 범위**로 승격한다.

## 8. 사용자 시나리오

### 시나리오 1. 모든 앱/창 중 하나로 전환

1. 사용자가 여러 macOS 앱과 여러 창을 실행 중이다.
2. 사용자가 모든 앱/창 모드 단축키를 누른다.
3. BokslTab이 앱 아이콘과 창/앱 타이틀로 구성된 리스트를 표시한다.
4. 사용자가 키보드로 원하는 창 또는 앱을 선택한다.
5. 사용자가 선택을 확정한다.
6. BokslTab이 선택한 창 또는 앱으로 전환한다.

### 시나리오 2. 현재 활성 앱의 다른 창으로 전환

1. 사용자가 VS Code 또는 Chrome처럼 여러 창을 가진 앱에서 작업 중이다.
2. 사용자가 활성 앱 창 모드 단축키를 누른다.
3. BokslTab이 현재 활성 앱의 창 목록을 표시한다.
4. 사용자가 원하는 창을 선택한다.
5. BokslTab이 해당 창으로 전환한다.

### 시나리오 3. 전환 취소

1. 사용자가 단축키로 앱/창 리스트를 연다.
2. 원하는 항목이 없거나 실수로 열었다고 판단한다.
3. 사용자가 `Escape`를 누른다.
4. BokslTab이 리스트를 닫고 기존 활성 창/앱을 유지한다.

## 9. 키보드 조작 요구사항

| 조작 | 요구사항 |
| --- | --- |
| 모든 앱/창 모드 열기 | 전역 단축키로 UI를 연다 |
| 활성 앱 창 모드 열기 | 별도 전역 단축키로 UI를 연다 |
| 다음 항목 이동 | `Tab` 또는 `ArrowDown` |
| 이전 항목 이동 | `Shift+Tab` 또는 `ArrowUp` |
| 선택 확정 | `Enter` 또는 단축키 release 기반 확정 |
| 취소 | `Escape` |
| 순환 이동 | 리스트 끝에서 다음 이동 시 첫 항목으로, 첫 항목에서 이전 이동 시 마지막 항목으로 이동 |

구현 단계에서 macOS 전역 단축키 처리 라이브러리/API의 제약에 따라 키 조합은 변경될 수 있다. 변경 시 PRD와 구현 계획에 기록한다.

## 10. UI 요구사항

- 앱/창 리스트 UI는 화면 중앙 또는 현재 활성 화면의 중앙에 표시한다.
- 각 항목은 앱 아이콘과 창/앱 타이틀을 포함한다.
- 현재 선택 항목은 파란색 focus ring 또는 유사한 하이라이트로 명확히 구분되어야 한다.
- 리스트가 길 경우 스크롤 또는 제한된 높이 내 표시를 허용한다.
- 창 썸네일 또는 실행 화면 캡처는 표시하지 않는다.
- 참고 이미지처럼 어두운 반투명 패널, 둥근 모서리, 큰 타이틀 텍스트를 MVP 기본 UI 방향으로 삼는다.
- MVP 디자인은 기능 검증을 위한 단순한 형태로 충분하다.
- 다크 모드 대응은 macOS 기본 스타일을 따르는 수준으로 한다.

## 11. macOS 권한/제약 관련 요구사항

### 11.1 접근성 권한

- 다른 앱/창을 정확히 활성화하거나 전역 키 이벤트를 안정적으로 처리하려면 접근성 권한이 필요할 수 있다.
- 특히 특정 창을 전면으로 가져오는 동작은 Accessibility API가 필요할 가능성이 높다.
- 권한이 필요할 경우 앱은 사용자에게 필요한 권한과 설정 위치를 안내해야 한다.
- MVP에서는 정교한 권한 온보딩 UI 대신 개발용 안내 메시지 또는 간단한 alert를 허용한다.

### 11.2 화면 기록 권한

- MVP는 화면 캡처나 창 썸네일을 표시하지 않으므로 화면 기록 권한을 요구하지 않는 것을 목표로 한다.
- 창 제목/소유 앱/윈도우 ID 조회 과정에서 macOS 버전에 따라 화면 기록 권한이 요구될 수 있는지 구현 전 확인해야 한다.
- 화면 기록 권한이 필요한 API는 가능한 한 피한다.

### 11.3 전역 단축키 제약

- 일부 단축키는 macOS 또는 다른 앱과 충돌할 수 있다.
- 충돌 시 MVP에서는 대체 기본 단축키를 코드 상수로 변경하는 방식을 허용한다.
- 사용자 설정 UI는 MVP에서 제외한다.

### 11.4 앱/창 활성화 제약

- macOS 정책에 따라 일부 앱, 시스템 프로세스, 특수 창은 활성화가 실패할 수 있다.
- 앱 활성화는 `NSRunningApplication`으로 가능하지만, 특정 창 전환은 추가 API가 필요할 수 있다.
- 활성화 실패는 크래시가 아니라 안전한 실패로 처리한다.

## 12. 예외 상황

| 상황 | 기대 동작 |
| --- | --- |
| 전환 가능한 앱/창이 없음 | 빈 상태 메시지를 표시하거나 UI를 열지 않는다 |
| 창 제목 조회 실패 | 앱 이름 또는 fallback 타이틀을 표시한다 |
| 아이콘 로딩 실패 | placeholder 아이콘을 표시한다 |
| 앱 이름 조회 실패 | process name 또는 bundle identifier를 표시한다 |
| 선택한 창이 전환 직전 닫힘 | UI를 닫고 안전하게 실패 처리한다 |
| 선택한 앱이 전환 직전 종료됨 | UI를 닫고 안전하게 실패 처리한다 |
| 전역 단축키 등록 실패 | 개발용 오류 메시지 또는 로그를 남긴다 |
| 접근성 권한 부족 | 필요한 권한 안내를 표시한다 |
| 창 단위 전환 실패 | 앱 단위 활성화 fallback 또는 안전한 실패 처리 |
| BokslTab 자체가 목록에 포함됨 | 기본적으로 제외한다 |

## 13. Acceptance Criteria

### AC-1. 모든 앱/창 모드

- Given 여러 macOS 앱과 창이 실행 중일 때
- When 사용자가 모든 앱/창 모드 단축키를 누르면
- Then 앱 아이콘과 창/앱 타이틀이 포함된 리스트가 표시된다.

### AC-2. 같은 앱의 여러 창 표시

- Given Chrome 또는 VS Code가 여러 창을 가지고 있을 때
- When 모든 앱/창 모드가 열리면
- Then 같은 앱의 여러 창이 각각 별도 항목으로 표시된다.

### AC-3. 활성 앱 창 모드

- Given 현재 활성 앱이 여러 창을 가지고 있을 때
- When 사용자가 활성 앱 창 모드 단축키를 누르면
- Then 현재 활성 앱의 창 목록만 표시된다.

### AC-4. 키보드 이동

- Given 앱/창 리스트가 열려 있을 때
- When 사용자가 다음/이전 이동 키를 누르면
- Then 선택 항목이 순환 이동한다.

### AC-5. 창 전환

- Given 앱/창 리스트에서 특정 창이 선택되어 있을 때
- When 사용자가 선택을 확정하면
- Then 해당 창이 foreground로 활성화된다.

### AC-6. 앱 전환 fallback

- Given 선택 항목이 창 정보 없는 앱 단위 항목일 때
- When 사용자가 선택을 확정하면
- Then 해당 앱이 foreground application으로 활성화된다.

### AC-7. 취소

- Given 앱/창 리스트가 열려 있을 때
- When 사용자가 `Escape`를 누르면
- Then 앱/창 리스트가 닫히고 기존 활성 앱/창이 유지된다.

### AC-8. 썸네일 제외

- Given 앱/창 리스트가 표시될 때
- Then 창 썸네일, 화면 캡처, 실시간 미리보기는 표시되지 않는다.

### AC-9. 안전한 실패

- Given 권한 부족, 창 종료, 앱 종료, 단축키 등록 실패 같은 예외가 발생할 때
- Then BokslTab은 크래시하지 않고 안내 또는 로그를 남긴다.

## 14. Assumptions

- 1차 MVP의 목적은 완성형 앱 출시가 아니라 프로세스 실험과 핵심 흐름 검증이다.
- 앱 전환뿐 아니라 **창 단위 전환은 MVP 필수**이다.
- 화면 캡처/창 썸네일을 사용하지 않으므로 화면 기록 권한은 요구하지 않는 방향으로 설계한다.
- 구현 언어는 macOS 네이티브 개발에 적합한 Swift를 기본으로 한다.
- UI는 SwiftUI를 우선 사용하되, 전역 단축키/앱 활성화/창 활성화/패널 표시 등 macOS 저수준 기능은 AppKit과 Accessibility API를 함께 사용할 수 있다.
- 앱 목록은 `NSWorkspace.shared.runningApplications`를 기본 출처로 한다.
- 창 목록은 CoreGraphics 윈도우 목록 API 또는 Accessibility API를 사용해 조회한다.
- 창 직접 전환은 macOS 제약이 크므로 구현 전 기술 검증이 필요하다.
- 단축키 기본값은 구현 중 충돌 여부에 따라 조정될 수 있다.

## 15. Open Questions

- 타깃 macOS 최소 버전은 무엇으로 할 것인가?
- 기본 단축키를 `Option+Tab`, `Option+Backtick`으로 확정해도 되는가?
- 모든 앱/창 모드의 정렬 기준은 최근 활성 창 순, 앱별 그룹, 앱 이름 순 중 무엇이 가장 적절한가?
- 활성 앱 창 모드는 “현재 foreground 앱의 창만”으로 확정할 것인가?
- 창 제목을 가져오려면 어떤 권한이 필요한가?
- 특정 창을 앞으로 가져오는 구현에 Accessibility API 사용을 허용할 것인가?
- 접근성 권한 안내를 alert로 처리할지, 별도 onboarding 화면을 둘지 결정이 필요한가?
- 구현 후 검증을 수동 시연 중심으로 할지, 일부 단위 테스트를 병행할지 결정이 필요한가?

## 16. 아키텍쳐(개발언어 라이브러리 등)

### 16.1 권장 기술 스택

| 영역 | 권장 선택 | 이유 |
| --- | --- | --- |
| 언어 | Swift | macOS 네이티브 API 접근이 쉽고 AppKit/SwiftUI와 자연스럽게 통합됨 |
| UI | SwiftUI + AppKit 보조 | 리스트 UI는 SwiftUI로 단순 구현하고, floating panel/activation은 AppKit 활용 가능 |
| 앱 목록 | AppKit `NSWorkspace` | 실행 중인 앱과 앱 아이콘/이름 조회에 적합 |
| 창 목록 | CoreGraphics `CGWindowListCopyWindowInfo` + Accessibility API 검토 | 창 제목, 소유 앱, 윈도우 ID, 전면 전환 가능성 확인 필요 |
| 앱 전환 | `NSRunningApplication.activate` | 앱 단위 foreground 전환에 적합 |
| 창 전환 | Accessibility API 또는 AppKit/CoreGraphics 조합 | 특정 창 focus/raise에 필요할 가능성이 높음 |
| 전역 단축키 | Carbon HotKey API, KeyboardShortcuts, HotKey 등 검토 | SwiftUI 단독으로 전역 단축키 처리가 제한적이므로 별도 방식 필요 |
| 테스트 | XCTest | Swift 프로젝트 기본 테스트 도구 |

### 16.2 권장 모듈 구조

- `AppCatalog`: 실행 앱 목록 조회, 앱 metadata 제공
- `WindowCatalog`: 창 목록 조회, 창 제목/소유 앱/윈도우 ID 관리
- `SwitcherItem`: 앱 항목과 창 항목을 모두 표현하는 공통 모델
- `HotkeyManager`: 모드별 전역 단축키 등록/해제
- `SwitcherState`: 현재 모드, 항목 리스트, 선택 인덱스 관리
- `SwitcherPanel`: 앱/창 리스트 UI 표시/닫기
- `AppWindowActivator`: 선택 앱 또는 창 활성화
- `PermissionAdvisor`: 권한 부족 감지 및 안내

### 16.3 의존성 원칙

- MVP에서는 의존성을 최소화한다.
- 전역 단축키 처리가 복잡할 경우 검증된 작은 Swift Package 사용을 허용한다.
- 창 전환 구현은 외부 의존성보다 macOS 네이티브 API 검증을 우선한다.
- 새 의존성을 도입할 때는 유지보수 상태, macOS 호환성, 라이선스를 확인한다.
